## 1. Status vocabulary

- **Package says complete**: the package's CURRENT/README marks its design/research phase complete. This does not prove execution or external validation.
- **Research/code evidence**: the cited archive or repository contains the described artifact/code.
- **Implemented narrowly**: code exists, but only within the scope and dependencies identified below.
- **Review proposal**: only present on an open, unmerged PR.
- **Open evidence**: the required experiment, user/site evidence, durable integration or decision is absent.
- **Not verified**: this pass did not inspect evidence at the scope needed to support a claim.

Do not infer customer validation, real Macau savings, production readiness, approval, or physical control from a Gate label or green CI.

## 3. What is actually on GitHub

### Current main (inspected repository baseline)

Main has a small VS-001 platform API path and versioned telemetry/recommendation/evidence schemas. It enforces a narrow SHADOW recommendation boundary, tenant/site matching and fail-closed behavior for unresolved graph/tariff adapters. The repository test uses static fixture adapters and an in-memory evidence repository.

The inspected main tree does **not** establish the full G7.6 acceptance slice: no implemented portal app, durable PostgreSQL adapter/migrations, live NATS/Temporal/MQTT stack, site telemetry connector, full simulator path or integrated source/load optimizer. The Go Edge executable is a bootstrap entrypoint; Python defines a recommendation boundary/model. G7.2 live R0 remains pending in main CURRENT. Therefore a partial code path and passing unit/CI checks must not be described as a completed MVP.

### PR #8 — product/architecture/governance review package

PR #8 is open and unmerged. It contains the research-derived Product Design/PRD/IA, logical architecture, product/UI governance and authority/research reconciliation. Those materials are reviewable drafts. Product and architecture choices remain owner/domain-review items; PR checks do not establish user validation or Gate closure.

### PR #10 — dispatch-first proposal and prototype

PR #10 is Draft/open/unmerged. It contains the economic source/load dispatch proposal, product/design traces, prototypes and a G7.9 Step 3 acceptance/repository trace. Its proposal connects the historic dispatch objective to a SHADOW-only workflow, but does not authorize device writing, settle site-specific capabilities, close G7.9 or select a production stack. The PR #10 G7.9 trace is a proposal for the next gate, not evidence that its outputs have been adopted on main.

### PR #14 — bounded optimizer experiment

PR #14 is Draft/open/unmerged. It contains a Python SHADOW assessment and finite-horizon search experiment with focused CI coverage. The PR itself documents omitted demand-charge windows, export revenue, degradation/reserve, comfort/safety, full EV/hot-water service, authenticated evidence and site validation. It is a bounded experiment, not the production optimizer or G7.9 Step 3 closure.

## 4. Decision and authority conflicts that must stay visible

1. **Historical G7.8 stack freeze versus current G6.9-R2:** G7.8 Step 3 records a Fastify/Node API baseline and OpenAPI + JSON Schema. Later active main authority D-064 keeps C+ provisional pending bake-off; D-068 requires a common semantic/AI-engineering comparison; current handoff leaves Step 3D pending. No accepted supersession record was found. Preserve both records until the owner/authority process resolves them.
2. **Product rollout sequence versus dispatch-first task:** G7.1/G7.5 sequence multi-energy dispatch after visibility/recommendations and even limited closed-loop stages. The current PR #8/#10 product drafts make dispatch planning the primary advisory task from the first experience. This is a meaningful sequencing change proposal, not an already-approved interpretation of the older pilot plan.
3. **Design completion versus empirical completion:** G7.3/G7.4 and G7.6–G7.9 package CURRENT files often mark a design/planning subgate complete while explicitly stating live runs, implementation or validation are next. Keep those statuses separate.
4. **Research archive versus repository adoption:** Authority v1.6.2 contains G7.3/G7.4 executable/research artifacts, but the PR #8 archive-to-main report says those exact artifacts are not imported into main. Summary decisions in main are not the same as importing the replay/controller sources and their evidence.

## 5. Product design implication

The strongest continuity from G7.2 to the current product proposal is **economic dispatch under operating constraints**. The first useful experience can be a same-horizon baseline/candidate SHADOW assessment, supported by evidence readiness, site topology, forecasts, tariff qualification, constraint explanation and replay. That is consistent with the domain objective while avoiding an unsupported claim of live control or realized ROI.

The main product decision still needing owner confirmation is whether this dispatch-first advisory workflow is the first commercial MVP promise, or whether rollout remains foundation-first (visibility/tariff readiness first, dispatch later). The documents do not justify silently treating either sequence as approved.
