### Decision D — What may the optimizer return when economic context is absent?

**Evidence:** PR #14 head `0b69b7b5db04a2f2454bec691ecc8f609facc552`. Its `generate_candidate()` request requires an `EconomicContext` with aligned import rates and its objective minimizes supplied grid-import energy charges. The separate `assess_schedule()` path can assess a supplied schedule without converting that physical profile into an economic result. The new PR #10 [optimizer-to-UI mapping trace](PR14-TO-DISPATCH-UI-RESULT-ADAPTER-TRACE-2026-10-05.md) records the exact enum and trust boundaries. The v2.3 no-tariff fixture now describes a supplied synthetic schedule assessment and explicitly says that it generates no optimized candidate.

| Option | Behavior with no eligible account/contract/tariff context | Consequence |
|---|---|---|
| **D1 — Assess supplied schedules only (recommended interim MVP boundary)** | Permit an explicitly supplied baseline/alternate schedule to receive scoped physical assessment. Do not generate an optimized candidate without an approved objective/economic context. Display economics NOT_CALCULATED/BLOCKED with reason. | Keeps economic dispatch claims tied to supported economics while preserving physical comparison. The UI must identify who supplied each schedule; no “optimized” label. |
| **D2 — Add a separately selected physical-only search objective** | Allow candidate generation only after the product owner explicitly selects and versions a non-financial objective and hard constraints, for example a stated import-peak objective. | Supports physical scenarios without tariff data, but it is not economic dispatch and cannot imply bill savings. Requires objective semantics, priority/constraint review, evidence gates and new acceptance corpus. |
| **D3 — Search with assumed tariff inputs** | Permit an explicitly assumed price profile to rank candidates, with output permanently SCENARIO_ONLY and no verified bill/savings claim. | Useful for research what-if analysis, but carries a higher risk that an assumed price is mistaken for a customer tariff. Requires strong provenance and UI separation from eligible customer economics. |

**Proposal for review:** Use D1 for the first SHADOW MVP. Keep D2 as a separately named scenario capability requiring an explicit product decision. Limit D3 to research mode until assumption provenance and operator comprehension are reviewed. This does not change PR #14 or approve its objective as production behavior.

**Acceptance invariant:** every assessment declares whether it validates a supplied schedule or returns a generated candidate, names the selected objective and evidence/version scope, and reports the optimizer run/search boundary. Missing economic context never becomes a zero price, default tariff, bill result, or savings claim. A supplied physical profile is not labeled optimized or dispatch-feasible without the corresponding constraint/service evidence.
