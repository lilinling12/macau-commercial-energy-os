## 2. Owner decisions requiring an explicit record

### Decision A — APP-11 logical ownership

PR #8's draft application catalog lists APP-01…APP-10 and has no dispatch-assessment operation. PR #10 proposes APP-11 as the logical source/load assessment task, composed with existing cost explanation, recommendation review and evidence/replay capabilities. This does **not** imply a new service, endpoint or deployment unit.

| Option | Meaning | Consequence |
|---|---|---|
| **A1 — Add APP-11 as a logical catalog capability** | APP-11 owns assessment identity/lifecycle and physical baseline/candidate result; it references one or more separately authorized economic evaluations and existing review/replay owners. | Catalog must version the new logical operation and status/reason semantics. It still does not mandate an endpoint or service split. |
| **A2 — Keep APP-11 as a named workflow only** | APP-05/06/07/08 compose the user workflow without a separate catalog operation. | The catalog must specify which capability owns assessment lifecycle, physical schedule result identity, scope selection and failure/replay semantics; APP-05 must not silently acquire physical optimization ownership. |

**Proposal for review:** A1 is the clearer logical owner for the dispatch task while preserving APP-05's settlement-calculation ownership. This is a recommendation in PR #10, not an approved decision. The same physical/economic separation and authorization rules apply under either option.

**Acceptance invariant under either option:** one physical schedule may have zero or more account-scoped economic evaluations; each child is independently authorized and evaluated. A physically permitted result may coexist with blocked/not-calculated economics. No site-wide aggregate cost/saving is implied without a separately approved aggregation objective.
