## 2. Model the scope before the status

A status without a declared scope is ambiguous. For review, represent each result dimension as:

`subject × time/scope × input revision × claim`

These are semantic axes, not proposed serialized field names.

1. **Request / authorization scope** — authenticated actor, tenant, authorized site(s), requested horizon and purpose. Authorization is a security precondition; a failed tenant/site authorization rejects the request as a whole and must not disclose the resource.
2. **Interval scope** — one half-open interval `[start, end)`, UTC instant plus site timezone/calendar context, and the exact input revision used. A gap, overlap or invalid timestamp affects the declared schedule scope; do not bridge it silently.
3. **Physical subject scope** — site boundary, meter/register, feeder, asset or telemetry point. Physical topology is distinct from account/contract applicability. Parent/child meters must not be added twice.
4. **Resource scope** — one identified PV inverter, ESS, HVAC/chiller, EV charging group, hot-water system or other asset, including the interval(s) and service horizon to which a bound applies.
5. **Settlement scope** — one independently authorized account × meter/register mapping × contract/tariff revision × bill component × effective interval. Multiple settlement scopes are separate evaluations unless a separately approved objective defines how to aggregate them.
6. **Claim scope** — one assertion, such as supplied-schedule balance, site import profile, resource feasibility, HVAC service, grid-import energy component, demand charge, export compensation, savings, replay or control.

Evidence references used by a future application need enough provenance to resolve the subject, validity/effective period, source, quality, freshness and immutable revision. PR #14's `EvidenceRef(ref, state)` is not that model: it has no subject, interval, source authorization, valid-time or immutable-snapshot fields, and the caller supplies its state.

## 3. Dependency matrix

| Claim/result | Minimum dependency scope | Missing, stale, conflicting or assumed input behavior | PR #14 evidence today |
|---|---|---|---|
| Schedule arithmetic / AC balance | Complete supplied values for every included interval and the declared bus boundary convention | Invalid or unbalanced included interval cannot be called balanced. A synthetic, assumption-tagged schedule may show arithmetic only as scenario; it is not measured site truth. | Checks PV partition and per-interval AC balance. |
| Site-qualified import profile / horizon peak | Authorized site boundary + effective point/meter mapping + interval observations/quality + complete interval coverage for the claimed window | If only part of a window qualifies, return an explicitly covered sub-scope; do not label a partial sum as the whole-window total. If no qualifying boundary exists, withhold site-qualified profile. Keep an arithmetic scenario distinct if product policy permits it. | Core `physical_evidence` is a request-wide tuple. Any UNKNOWN/STALE core reference blocks the entire physical assessment; no asset/interval evidence scope or coverage is returned. |
| PV local use / export / curtailment | PV output and point/mapping scope per interval; inverter/curtailment capability for a curtailment claim; separately, export meter and topology for physical export | Missing export/payee/contract evidence withholds the dependent export/economic claim. Do not infer exports from residual balance or equate export with credit. | Checks a declared PV partition and has a resource-specific curtailment evidence reference. No authenticated topology/export scope. |
| ESS electrical dispatch | ESS identity + interval power limits + SOC observations and transition/efficiency bounds + reserve policy over the full ESS schedule | Withhold ESS-feasibility claim when its own required evidence is absent/stale. Preserve a separately qualified non-ESS or arithmetic profile only if represented explicitly. A known limit violation is infeasible; an unknown limit is not. | ESS has resource-level limits/state references; unqualified ESS cases can retain the import profile. SOC continuity and boundary conditions are checked when supplied. No authenticated SOC source or independent no-ESS alternative. |
| Flexible-load electrical schedule | Asset identity + interval power envelope/availability and any required ramp/recovery limits | Withhold feasibility for the affected asset; unchanged loads do not imply controllability. A changed schedule may be shown as scenario only if clearly qualified, never as service-feasible. | Changed load limits are keyed by asset ID and can withhold that asset's claim. No effective-time/interval-specific service bounds. |
| HVAC / EV / hot-water service | Per-resource service model and full service horizon: comfort/recovery/rebound; departure energy/deadline; delivery temperature/quantity, respectively | `NOT_ASSESSED` until a qualified service model and evidence exist. Electrical balance is not a service pass. | Explicitly not modeled; claim withheld. |
| Grid-import guard | Guard definition, boundary, effective intervals and authorized evidence source | Unknown/stale guard withholds guard-compliance claim. Known exceedance is infeasible within the declared guard scope. | Resource-like guard reference; request-wide single limit. |
| Import-energy component | One authorized settlement scope, effective contract/tariff/rules and one verified exact rate per priced schedule interval | Price only exactly covered eligible intervals and identify coverage. No covered interval means no amount. A tariff boundary within an interval is withheld unless finer energy evidence/rules support exact allocation. | Single `EconomicContext`; account/meter, contract and tariff must be VERIFIED; exact verified rates are evaluated per interval; partial interval coverage is supported. |
| Demand charge / Pu | Applicable billing-period register or qualified interval reconstruction + tariff meter window, demand measurement policy, period and rule revision | Withhold unless the contractual measurement window and eligible data are known. Scheduler horizon peak is not billing-period Pu. | Not evaluated. |
| Export compensation / cross-site credit | Exported energy at the settlement point + interconnection/contract/rate/payee/account and, for cross-site credit, applicable allocation/settlement authority | Physical export may be shown separately where metered. Compensation/credit stays withheld without all relevant rights and applicability evidence. | Always withheld; no settlement evidence integration. |
| Savings / full bill | Complete relevant settlement components, a validated baseline and comparison period, approved adjustment/M&V method and required bill evidence | Do not derive savings from partial energy charges or scenario objective. | Always withheld; only a bounded import-energy component can be calculated. |
| Replay / provenance | Immutable input, mapping, rule, model, optimizer, code/build and output revisions, plus retention/authorization | Report reproducible, divergent, incomplete or unavailable; never substitute current inputs silently. | Determinism is checked for a bounded repeated input; no durable snapshot or replay service. |
| Controllability / device control | Site-qualified capability, safety authority, authenticated command boundary and separate approved control Gate | Outside MVP: display unavailable/withheld. No review action can become a command. | Always withheld; no command path. |

## 4. Status composition rules for UI and application

Keep these independent; do not collapse them into one green/red readiness badge:

- **Lifecycle:** accepted, queued, running, completed, failed/cancelled. This says whether an operation ran.
- **Assessment per declared scope:** complete, partial, blocked, infeasible, not calculated. This says what portion was evaluated.
- **Claim disposition:** allowed or withheld. A claim is either displayable within its declared qualification or withheld; “partial” belongs to claim scope/coverage, not a third disposition.
- **Qualification/provenance:** measured, forecast, scenario, synthetic, assumed, stale, unresolved or verified under an application policy. Evidence state is not assessment state.
- **Service outcome per resource:** not assessed, pass, violation or unknown. `PASS` requires qualified service evidence; it cannot be inferred from electrical balance.
- **Economic result:** per settlement scope and component, with currency, period, coverage and rule references. A partial amount must be labeled as a partial component, not a bill total or savings.
- **Human review:** append-only disposition with actor/time/result revision after identity, persistence and authorization exist. It is distinct from execution authority.

For any partial result, show the scope numerator/denominator or exact covered intervals and the missing scope. A profile for three covered intervals must not be visually presented as a six-hour total. Localized labels must preserve the same semantics in Traditional Chinese, Portuguese and English; translating only status words is insufficient.

## 5. Acceptance corpus to bind to future implementation

These cases are **design acceptance proposals**. They are not represented as new passing tests.

| Case | Input condition | Required result |
|---|---|---|
| E-01 Authorization | Actor requests another tenant's site or settlement scope | Reject whole request before assessment; no existence/result leakage; audit safe denial. |
| E-02 Whole-window alignment | Baseline/candidate differ in interval set, contain a gap/overlap, or an interval is unbalanced | Reject the declared comparison as blocked/invalid or infeasible according to a reviewed error taxonomy; never compute a full-window total from malformed rows. |
| E-03 Scoped stale telemetry | One of six intervals has stale mapped meter evidence; five are valid | Return only the five-interval qualified physical scope as PARTIAL with exact coverage and affected claim reasons, if and only if the API can preserve independent interval results. Do not interpolate the sixth or report a six-hour total. If one stale point invalidates the bus balance for its interval, withhold that interval's balance and downstream claims. |
| E-04 Overlapping meter topology | Parent meter and child feeder both report energy for the same load | Do not sum overlapping registers. Return a conflict/mapping error or calculate from one authorized non-overlapping boundary. |
| E-05 Resource isolation | HVAC envelope is missing while an independent, unchanged ESS/PV profile is otherwise qualified | Withhold HVAC variable-dispatch/service claims. Preserve only claims that do not depend on HVAC flexibility; never infer controllability. |
| E-06 ESS state | One required ESS SOC endpoint or efficiency/reserve bound is unknown | Withhold ESS feasibility and ESS-derived benefit. Preserve an independently qualified no-ESS result only if separately represented; otherwise mark affected horizon scope partial/blocked. |
| E-07 Independent economic rate gap | Five of six intervals have unique VERIFIED exact import rates; sixth is missing/stale | Return a five-interval import-energy component marked PARTIAL with covered intervals and explicit excluded interval; demand/full-bill/savings remain withheld. |
| E-08 Rate boundary | One schedule interval straddles two effective rates and no finer energy distribution is supplied | Withhold that interval's charge; never price all energy at the interval-start rate. Other eligible intervals can remain separately visible. |
| E-09 Settlement identity | Physical site profile is qualified, but account/meter mapping or contract applicability is absent | Keep physical result if otherwise allowed; mark that settlement-scope economics NOT_CALCULATED/BLOCKED with reason. No money placeholder zero. |
| E-10 PV export without payee | Metered export exists, but compensation right/payee/account is unproven | Permit only the evidenced physical-export claim; withhold credit, revenue, netting, cross-site supply and savings. |
| E-11 Pu scope | Horizon maximum is available; billing period/Pu window is unknown | Show “horizon peak” with exact period only; withhold Pu/demand charge and tariff ranking dependent on Pu. |
| E-12 Service outcome | Balanced candidate shifts HVAC/EV/hot-water but no qualified response/service model exists | Show electrical scenario only; each resource service result is NOT_ASSESSED; no feasible/comfortable/ready claim. |
| E-13 Replay | Current tariff/model differs from the immutable revision referenced by an old run | Replay the pinned revision or return explicit unavailable/divergent status; never replace it with current evidence. |

## 6. Implementation boundary and next dependency

The safe next engineering sequence is:

1. Product/domain/security review the scope and status meanings above, especially E-03's partial-window behavior and the minimum shared evidence required to qualify a site boundary.
2. Resolve T0 authority and APP-11 ownership; decide which existing catalog responsibilities compose this capability. Keep this proposal schema-neutral until contract-authority and canonical generation decisions are approved.
3. Define an authenticated evidence resolver and immutable input-snapshot semantics before allowing caller evidence state to qualify claims.
4. Add scope-aware physical result coverage and independent settlement-scope results behind a versioned adapter; preserve current conservative full-request blocking unless the result can explicitly report interval/subject coverage.
5. Implement the acceptance corpus against the approved contract and UI projection; run exact-head checks and record real covered states. Do not call the prototype a pilot or real-site optimizer.
6. Keep all assessment paths read-only and SHADOW. Device control is out of scope.
