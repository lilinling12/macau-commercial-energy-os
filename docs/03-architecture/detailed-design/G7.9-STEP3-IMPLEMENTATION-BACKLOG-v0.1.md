# G7.9 Step 3 — Stack-Neutral Implementation Backlog v0.1

**Status:** Review proposal. This is a task decomposition, not an approved implementation plan, architecture freeze, production contract, or Gate exit.
**Date:** 2026-10-05
**Basis:** G7.9 Step 2 source package; current main tree `a897bf0b1e7e6ceea3862d7d87fa288ecca08203`; PR #8 product/architecture proposals; PR #10 Step 3 acceptance/repository trace; PR #14 bounded optimizer experiment.
**Purpose:** Translate Step 3 output 4 (repository implementation tasks) into sequenced work packets while preserving unresolved owner and authority decisions.

## 1. Planning rules

- “Ready” means the task has enough semantics to be reviewed or implemented without guessing an unresolved owner decision. It does not mean it is approved.
- Stack-neutral tasks may define domain meaning, trust boundaries, acceptance behavior, path ownership and migration requirements. They must not introduce a production framework, wire format, generator, database schema or deployment topology.
- No task may infer site tariff, export rights, equipment controllability, savings, comfort feasibility or Macau site truth from synthetic fixtures.
- The MVP boundary remains read-only ingestion plus SHADOW assessment/review. No equipment command path is in this backlog.
- G7.9 Step 3 remains open until its source-linked exit criteria are reviewed and accepted.

## 2. Dependency sequence


### T1 — Complete domain and evidence semantics

**Target paths:** `docs/03-architecture/domain/` (proposed; confirm repository naming convention before adding) and the existing G7.9 Step 3 design record.
**Status:** Semantically ready for domain/product review; schemas remain deferred.

**Work**
- Close the Step 2 model gaps: Site relationships, site clock/timezone, building/meter boundary, physical topology versus settlement applicability, effective-dated asset/point mappings.
- Specify half-open interval meaning, UTC plus site-local representation, unit/sign convention, measurement quality/freshness, source/received/valid times, immutable snapshot identity and forecast provenance.
- Keep physical energy balance independent from account/meter/contract settlement. Define claim states and reason codes for physical profile, bill-grade cost, savings, export compensation, controllability, comfort/service and replay.
- Define unknown-input behavior that blocks only affected claims or operations; never fill gaps with presumed capability.
- Decide semantic ownership for Site, settlement applicability, evidence/manifest, forecast/constraint, assessment/result, recommendation/review and replay records without deciding whether each becomes a table or service.

**Acceptance evidence**
- Entity/relationship and glossary review maps every added concept to exact Step 2 source or labels it as a Step 3 proposal.
- Examples cover tariff-free physical comparison, missing site mapping, PV export without payee evidence, missing ESS SOC/efficiency, unknown flexible-load service bounds, and time/effective-date boundaries.
- Apply the schema-neutral claim-specific readiness matrix in `G7.9-STEP3-DISPATCH-CONTRACT-IMPLEMENTATION-MAP-v0.1.md` §3: assessment status and per-claim ALLOWED/WITHHELD remain orthogonal; missing evidence blocks only the affected scope/claim when independent evidence supports the remainder. Include a tariff-free physical profile, ambiguous mapping, PV export/payee gap, ESS unknown state, unqualified flexible load, unknown Pu window, crossing tariff-effective boundary, and stale/clock-ambiguous input.
- Product/domain reviewers accept terminology and expected outcomes; unresolved cases have owners and evidence requests.

### T2 — Freeze a boundary-specific contract profile

**Status:** Blocked on T0 contract-authority decision.

**Acceptance evidence**

- This task does not choose an API framework or deployment split.

### T3 — Define API module responsibility and authorization

**Target paths:** existing `implementation/platform-api/` only after design approval; target module paths depend on T0.
**Status:** Trust semantics are designable now; implementation waits for T0/T2.

**Work**
- Resolve authenticated principal → tenant → organization/site authorization from trusted identity context; request-body tenant/site identifiers are selectors, never authority.
- Define operations only for accepted APP ownership: submit assessment, read lifecycle/result, append SHADOW review, inspect evidence/replay where authorized.
- Define request idempotency, duplicate/conflict behavior, asynchronous acceptance versus completed result, pagination and safe error disclosure.
- Preserve existing APP-05/06/07/08 responsibilities and APP-09 entitlement / APP-10 audit roles.

**Acceptance evidence**

- Cross-tenant and unauthorized-site cases deny without leaking existence or result data.
- Duplicate requests return one durable logical assessment; queue acceptance is not reported as completed.
- Review actions cannot create or authorize an equipment command.

### T4 — Design durable assessment, evidence pinning and replay

**Target paths:** approved persistence/migration design under `docs/03-architecture/detailed-design/`; later implementation under the selected storage modules.
**Status:** Design requirements are ready; physical schema waits on T0/T1/T2 and retention/security classification.

**Work**
- Pin input evidence, topology, tariff/contract applicability, forecast, constraint, policy, optimizer and build versions for every immutable assessment.
- Define lifecycle transitions, retry/idempotency, terminal errors, append-only review history and result immutability.
- Specify tenant-scoped uniqueness and access, transactional boundaries/outbox only if justified, retention/deletion/legal-hold requirements, backup/restore and migration compatibility.
- Define replay outcomes: reproducible, divergent, incomplete or unavailable; never silently substitute current inputs for missing historical ones.
- Separate assessment persistence from device state and command authorization.

**Acceptance evidence**
- State transition table and failure matrix reviewed by domain/security/architecture owners.
- Restart/retry/duplicate tests demonstrate durable single identity and immutable result.
- Restore/replay test proves the original inputs or reports the explicit unavailable state.
- Migration/rollback or forward-fix plan is rehearsed on representative data before any production migration.

### T5 — Specify the read-only Edge boundary

**Target paths:** `implementation/edge-runtime/` after authority review; current Go entrypoint is bootstrap evidence only.

### T6 — Define a replaceable optimizer boundary and acceptance corpus

**Target paths:** `implementation/optimizer/` and versioned synthetic fixtures only after T1/T2 semantic review.
**Status:** Existing PR #14 is an experiment, not an accepted solver.

**Work**
- Normalize immutable inputs and return schedules plus diagnostics; the optimizer cannot fetch or self-certify evidence.
- Specify hard constraints separately from soft objectives; unknown hard constraints block or exclude the affected resource by explicit policy.
- Include interval balance, ESS power/SOC/efficiency/terminal reserve, load shift/rebound, service/comfort bounds, horizon boundaries, infeasible and timeout outcomes.
- Pin objective/constraint version and deterministic tie-breaking where reproducibility is required; bound CPU, memory, horizon and search work.
- Preserve independent physical feasibility and economic evaluation; do not let the optimizer invent tariff or settlement semantics.
- Carry the T1 scope/claim readiness explicitly into the optimizer/application result boundary. Current PR #14's request-wide unknown/stale evidence gate blocks the whole physical assessment and its economic evaluator has no partial claim ledger; this remains an experiment limitation to review, not an accepted implementation.

**Acceptance evidence**
- Synthetic and property-based cases verify balance, bounds, terminal SOC, rebound and failure labels.
- Same pinned input/version produces deterministic result within declared tolerance, or explicitly documents nondeterminism and replay limits.
- Adversarial oversized/invalid inputs terminate within resource budgets.
- Comparison against a simple baseline is documented; no “optimal” claim without a defined objective, constraints and benchmark.

### T7 — Integrate one end-to-end SHADOW vertical slice

**Target paths:** approved API, contract, persistence, optimizer, portal and fixture modules after T2–T6.
**Status:** Not implementation-ready until dependencies close.

**Work**
- Select one synthetic fixture and one contract-authorized, read-only data path.
- Implement intake → readiness → physical schedule comparison → optional eligible economic calculation → immutable result → SHADOW review → replay.
- Render independent physical/economic/review/replay states in the UI. UI labels must correspond to API states and evidence references.
- Keep PV export, account credits, savings and EV/hot-water flexibility withheld unless the fixture explicitly supplies the required evidence.
- Maintain accessible desktop/tablet/mobile states and do not expose device execution.

**Acceptance evidence**
- Contract, domain, security, integration, browser and replay checks pass on the same pinned fixture/build.
- UI and API agree on blocked/partial/eligible states and explain reasons.
- An independent reviewer can reconstruct inputs, assumptions and output without relying on transient logs.
- Synthetic success is clearly identified and not represented as Macau/site validation.

### T8 — Operations, release and pilot-readiness evidence

**Target paths:** repository runbooks, deployment/recovery workflows and readiness record; exact locations follow governance review.
**Status:** Later, after a successful T7 slice and separately authorized pilot discovery.

**Work**

- Document secrets, access review, dependency/security scanning, release signing, schema evolution, deployment, rollback/forward-fix and incident response.
- Establish SLO/error budgets only from a bounded workload and user-critical path; do not invent targets without an operating requirement.
- Define pilot evidence prerequisites: site authorization, meter/asset mapping, anonymized bills/contract, data retention basis, operator roles, baseline/M&V plan and independent review.

**Acceptance evidence**
- Rehearsed deployment and recovery, restore evidence, access/security review and actionable runbooks.
- Pilot readiness checklist has named evidence owners and no unresolved critical blockers.
- Site/customer claims are supported by approved, traceable evidence; synthetic tests are not substituted.
