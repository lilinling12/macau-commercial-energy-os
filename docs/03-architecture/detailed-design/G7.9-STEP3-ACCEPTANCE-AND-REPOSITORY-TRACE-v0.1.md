## 5. Proposed logical assessment contract and state separation

Before selecting wire fields, agree the following semantic envelope:

### Request intent

- Authorized site selector; tenant/actor/roles come from a trusted server context.
- Explicit analysis purpose: physical import/profile shaping, or evidence-qualified economic comparison. Do not conflate a physical profile with a bill or savings claim.
- Start-inclusive/end-exclusive planning horizon, site timezone and interval grid. The planning grid is not the utility's billing/demand measurement interval.
- Immutable telemetry, topology, forecast and constraint snapshot references; baseline construction policy; objective/policy version; optional economic-context reference.
- Idempotency key scoped to principal and authorized site. Same key + same normalized semantic request returns the same assessment; same key + changed semantic inputs yields conflict.

### Separate status dimensions

1. **Request lifecycle:** rejected, accepted/pending, running, completed, failed.
2. **Physical readiness/result:** blocked, partial, feasible, infeasible, or not assessed, with missing/violated constraints.
3. **Economic eligibility/result:** blocked, partial, eligible, not calculated; every component has evidence/provenance and allowed/withheld reason.
4. **Recommendation/review:** SHADOW proposal and append-only reviewed/request-evidence/dismissed state.
5. **Replay:** reproducible, divergent, incomplete, unavailable; original result stays immutable.

One green state must not imply these independent dimensions all succeeded. Exact wire enum vocabulary remains open for owner/G1 review.

## 6. Physical dispatch and settlement acceptance

For each candidate, baseline and candidate use the same authorized site, horizon, interval boundaries, timezone, topology version and input snapshot. A physical balance may be expressed as:

`grid import + PV used + ESS discharge + evidenced other supply = site load + ESS charge + evidenced export + curtailment`.

Every term requires explicit unit, sign, source/evidence state and interval semantics. Never add a bill-credit assumption to the physical balance. Financial settlement is a separate evaluator over the applicable account/meter, effective contract/rate, billing interval, demand rules, tax/adjustment terms and export compensation evidence.

| Acceptance case | Required result |
|---|---|
| Missing or ambiguous site/meter/asset mapping | Block the affected physical schedule; identify the unresolved link; do not guess topology. |
| Unknown tariff/account applicability or CEM Pu interval | Preserve a permitted physical profile if inputs allow; withhold bill-grade totals, demand-savings and tariff-sensitive ranking. Do not substitute the scheduler interval for the billing interval. |
| PV physical generation present, export contract/recipient unknown | Permit only evidence-backed on-site flow; export compensation/netting remains withheld. No cross-building credit inference. |
| ESS limits, SOC or efficiency absent/stale | Do not claim ESS-feasible schedule; exclude or mark scenario-only per reviewed policy. Enforce terminal SOC/effective constraints when included. |
| HVAC comfort/rebound constraints unknown | Do not label HVAC schedule comfortable/controllable/feasible; disclose shifted and rebound intervals. |
| EV charging window or hot-water service requirement unknown | Keep those loads unchanged or scenario-only; do not claim controllability or service satisfaction. |
| Demand Guard or safety limit binds | Candidate must respect it or return infeasible/blocked with a reason; optimizer cannot relax the constraint. |
| Repeated request / restart / missing pinned input | Preserve idempotency and durable lifecycle; never report completion from a queue acknowledgement; report replay as incomplete/unavailable rather than substituting current inputs. |

The PR #10 v0.5 fixture and PR #14 bounded search can exercise portions of physical balance, HVAC shift/rebound, ESS SOC and synthetic multi-load behavior. They do not establish full tariff correctness, field capability, comfort/safety feasibility or Macau site validity.

## 10. APP-11 ownership versus APP-05/06/07/08

### Source facts

- PR #8's `MVP-APPLICATION-AND-EVENT-CONTRACT-CATALOG-v0.1.md` defines APP-05 as **Request an economic assessment**, APP-06 as **Read a cost result and its explanation**, APP-07 as **Review a SHADOW recommendation**, and APP-08 as **Inspect evidence and request replay**. APP-09 manages organization membership/site entitlement; APP-10 reads operational audit/integration status.
- The catalog intentionally separates product capability, logical operation, wire contract, persistence, domain semantics, authorization, and transport. It does not select protocol, endpoint, schema authoring, broker, or runtime.
- PR #10 proposes APP-11 as a source/load schedule-assessment capability that connects APP-05/06/07/08. Its map says APP-11 has not been added to the catalog and leaves its wire format, endpoint, worker and deployment undecided.
- PR #8 Owner Decision #20 presents a distinct logical APP-11 capability as a review recommendation, not a recorded owner approval.

### Recommended logical split for owner review

Keep APP-11 as the **dispatch-assessment orchestration capability**, with APP-05/06/07/08 preserving their independent semantics:

1. APP-11 owns request identity/lifecycle and physical baseline/candidate schedule assessment for a common site/horizon. It pins topology, telemetry, forecasts, capability and constraint inputs; reports physical readiness/feasibility and withheld claims.
2. When an economic comparison is requested and eligible, APP-11 references or invokes APP-05 for each comparable schedule under the applicable account/meter/contract/tariff context. APP-05 remains the owner of economic calculation; APP-06 owns the resulting cost explanation. APP-11 must not recompute settlement or label an unverified scenario as a bill.
3. APP-07 owns a separate append-only human disposition for the immutable SHADOW recommendation. APP-11 completion/review cannot authorize equipment execution.
4. APP-08 owns evidence inspection and replay of pinned inputs/results. APP-11 stores references; it does not redefine replay truth or mutate history.
5. APP-01/02/03/04 provide authorized scope, data health, telemetry and model prerequisites. APP-09/10 remain access-administration and audit capabilities, not dispatch commands.

This makes APP-11 a distinct **logical** user task, not a decision to add an endpoint, service, database record or independently deployed component. It avoids overloading APP-05 with schedule optimization while keeping cost, review and replay authority in their existing owners.

**Alternative for review:** extend APP-05 with a `SOURCE_LOAD_DISPATCH` analysis kind and omit APP-11. That is viable only if APP-05 is explicitly expanded to own physical schedule generation, constraints and lifecycle; it increases coupling between settlement and physical scheduling and would require revising its existing catalog ownership. The current evidence better supports a separate APP-11 capability that composes APP-05/06/07/08. This recommendation is not approved and does not settle APP-11's final request/status vocabulary.

## 13. Site/meter/account settlement boundary crosswalk — 2026-10-05

Added `docs/03-architecture/detailed-design/SITE-METER-ACCOUNT-SETTLEMENT-MODEL-v0.1.md` as a stack-neutral Step 3 domain proposal. It translates G7.9 Step 2's Site/entity omissions and main D-013/D-005/D-055/D-077/U-025 boundaries into conceptual relationships and testable acceptance cases. It distinguishes application tenant, organization/legal party, site, building, electrical connection point, meter/register, supply installation/account, tariff, PV interconnection/purchase agreement, bill snapshot and evidence reference. It requires effective-dated evidence-backed mappings; independent account-level tariff calculations; gross import/export preservation; replay against historical mapping; and no physical or economic cross-site edge by default.

Official CEM bill/tariff sources support the separate contract holder, installation address, contract number, consumption period, meter multiplier, subscribed demand and tariff-group fields; Groups B/C/D have account-class and billing-period demand semantics, and Tariff Clause Adjustment is published quarterly. These facts support the boundary model but do not prove the pilot's actual accounts, meters, Pu interval, agreement, cross-account rights or bills. The model is conceptual and does not create canonical tables/schemas or supersede D-055's initial economic scope. Remaining cardinalities must be validated against an authorized site's asset diagram, bills and contracts.
