## 2. Proposed logical request contract

An authenticated principal and trusted authorization context are resolved before request data is used. Tenant ID, actor identity, permissions and roles come from that trusted context, never from caller assertions. A caller-supplied site reference is only a selector and must be authorized and resolved before work is accepted.

| Field | Meaning | Validation / boundary |
|---|---|---|
| clientRequestId | Caller-generated idempotency key for this semantic request. | Required, scoped to authenticated principal + authorized site; identical key and identical normalized request returns the same operation reference. Same key with different semantic inputs is a conflict. |
| siteRef | Requested site selector. | Required; resolved through authorized site mapping. Do not disclose whether an unauthorized site exists. |
| planningWindow | start, end, timeZone, intervalSeconds and a clock-policy reference. | Start-inclusive/end-exclusive interval semantics. IANA timezone and site clock policy required. Settlement intervals must not be inferred from this calculation grid. |
| inputSnapshotRef | Immutable telemetry, mapping and quality snapshot selected for the assessment. | Required for replayability; missing or stale required inputs block or limit the associated claim class. Never silently substitute “latest” after acceptance. |
| objective | One declared objective, such as PHYSICAL_IMPORT_PROFILE or VERIFIED_ECONOMIC_COST. | Physical shaping and verified customer economics are separate requests/claim classes. Do not rank scenario-only cost as bill-grade. |
| baselinePolicyRef | Versioned baseline construction policy. | Required; baseline and candidate use the same site, horizon, interval grid, input snapshot and boundary conventions. |
| constraintRefs | Versioned equipment, operating, safety, comfort and site-policy constraints. | Each constraint has source/evidence, scope and effective interval. Unknown constraints cannot be converted to zero, unlimited or relaxed values. |
| economicContextRef | Optional account/contract/tariff/evaluator context reference. | Required for a bill-grade economic objective. If absent/unresolved, economic output is BLOCKED or NOT_CALCULATED; a separately permitted physical result may still be returned. |
| optimizerPolicyRef | Versioned solver/policy configuration when assessment runs. | The service pins the actual resolved version and build into the result. No optimizer is selected by this design. |

The service returns a stable assessment reference only after authorization, validation and durable acceptance. A synchronous HTTP response, queue receipt or broker acknowledgement must not be described as completed work. Exact transport and status codes remain open.

## 3. Proposed result semantics

Return distinct status dimensions so a single green badge cannot imply valid data, economic readiness, physical feasibility, recommendation review and execution.

| Dimension | Candidate vocabulary | Meaning |
|---|---|---|
| Request lifecycle | REJECTED, ACCEPTED, RUNNING, COMPLETED, FAILED | Intake and processing progress. ACCEPTED means durably recorded, not successfully optimized. |
| Physical assessment | NOT_REQUESTED, COMPLETE, PARTIAL, BLOCKED, INFEASIBLE, FAILED | Whether a physical schedule comparison was formed for the declared scope. |
| Economic assessment | NOT_CALCULATED, COMPLETE, PARTIAL, BLOCKED, FAILED | Whether a separate settlement evaluator could assess the declared economic scope. |
| Evidence readiness | Repository-approved evidence classes plus explicit missing/expired/ambiguous state | Provenance/quality classification; evidence category is not a calculation status. |
| Recommendation review | NOT_REVIEWED, REVIEWED, REQUEST_EVIDENCE, DISMISSED | Append-only human disposition against a recommendation version. No disposition authorizes device writes. |

These are proposed vocabularies; reconcile with the existing PR #8 catalog, D-065, repository evidence vocabulary and tariff-result proposal before treating them as canonical. If work fails without producing a result, return no partial numeric result unless its semantics and retained scope are explicit.

### Physical schedule

For each interval, report the declared physical boundary and quantities needed to reconcile it, including grid import, on-site PV generation/use/export/curtailment where evidenced, ESS charge/discharge/SOC where modelled, end-use load, losses and quality/evidence references.

A simplified balance may be:

gridImport + pvUsedOnSite + essDischarge = siteLoad + essCharge + export + conversionLosses

The actual terms depend on the metering boundary and equipment topology. Do not count one PV quantity twice, assign one producer to multiple consumers, or infer export rights from the physical balance. If SOC, efficiency, loss, comfort or rebound is omitted, state that omission and lower the supported readiness/claim class.

Each interval identifies start/end, site timezone/clock policy, interval convention, quantity/unit/sign convention, baseline/candidate values and input lineage. Forecast values identify issue time, valid period, model/build, uncertainty and source coverage; measured observations remain separate from forecasts.

### Economic evaluation

Economic output is a separate reference/result, not embedded as a generic estimatedValue on a physical schedule. It identifies the authorized settlement scope (account/stream), effective contract/tariff/evaluator versions, currency and rounding policy, component amounts/quantities, input coverage, exclusions, unresolved reasons and evidence references. Preserve exact monetary semantics from the existing cost-result design. If applicable tariff or account evidence is unresolved, withhold bill-grade totals, savings and PV export credit.

#### Public tariff-rule and source-applicability boundary

The public CEM Group B page describes billed demand as `0.2Pc + 0.8Pu`; `Pc` is subscribed active demand in kW and `Pu` is the highest measured demand in the billing period. Separately, Group B eligibility is stated using subscribed apparent demand in kVA and monthly kWh. The contract/data design must not conflate these eligibility quantities with billed active demand, and must not infer the customer's tariff group from a building category. Source: [CEM Tariff Group B](https://www.cem-macau.com/en/customer-service/billing-service/tariff-group-b/) and [Administrative Regulation 25/2022](https://bo.io.gov.mo/bo/i/2022/26/regadm25.asp).

For a Group B evaluation, preserve the tariff class, account/contract applicability, subscribed-demand values and units, full billing period, metering class, tariff calendar, active/reactive quantities, effective-dated TCA, source/evaluator version and evidence references. The published formula does not establish the actual meter's Pu measurement/integration window. Until that window and the customer tariff/account match are evidenced under U-001, the Group B demand component is unresolved; return a scoped PARTIAL/BLOCKED result as appropriate, and withhold a bill-grade total or demand-savings claim. Never substitute the assessment grid (hourly or otherwise) for the Pu measurement interval.

CEM publishes TCA by effective quarter; the public page currently displays 2026 Q3 at MOP 0.36/kWh effective 2026-07-22. This must be versioned as a dated input, not embedded as a timeless constant: [CEM Tariff Clause Adjustment](https://www.cem-macau.com/pt/customer-service/billing-service/tariff-clause-adjustment/).

Macao's PV interconnection regulation and CEM's published feed-in schedule establish public mechanisms subject to installation/technical and programme conditions, not cross-account netting. An export-compensation component requires evidence for the installed capacity tier, approved interconnection, applicable purchase terms, export meter, effective rate and payee/account. A separate building's PV must not become this account's bill credit by physical-flow inference: [Administrative Regulation 20/2014](https://bo.dsaj.gov.mo/isapi/go.asp?d=rega-20-2014cn); [CEM PV Feed-in Tariff](https://twww.cem-macau.com/en/go-green/photovoltaic-system-%28pv%29/feed-in-tariff/).

### Claim ledger

For every displayed economic or operational claim, include a claim class, state (ALLOWED or WITHHELD), evidence/assumption references and stable reason codes. At minimum distinguish physical profile, peak import, bill-grade cost, projected savings, PV export compensation, cross-site netting, comfort/service feasibility and device controllability. A missing claim is not implicitly zero.

#### Claim-specific readiness and withholding behavior (T1 proposal)

The assessment has independent physical and economic results; individual displayed claims also need independent eligibility. A blocked claim must not erase an unrelated result that has qualified evidence, while a partial result must not be promoted to a complete bill/feasibility conclusion. This behavior is schema-neutral and remains subject to product, domain, tariff and security review.

| Evidence condition | Physical assessment and permitted claims | Economic assessment and permitted claims | Required withheld claims / behavior |
|---|---|---|---|
| Site boundary, topology, mapping and interval observations qualify; account/contract/tariff context is absent. | A scoped measured or explicitly labeled scenario profile may be COMPLETE; a horizon import peak may be reported with the exact horizon and meter boundary. | NOT_CALCULATED or BLOCKED for bill-grade scope, with a stable reason. | No bill total, tariff ranking, savings, demand-charge effect, export compensation or cross-site credit. A physical horizon peak must not be named Pu. |
| Required site/meter/asset mapping is absent, ambiguous, conflicting or not effective for the assessed time. | BLOCKED only for the affected physical boundary/scope; identify the unresolved link. Do not infer or silently choose a mapping. | BLOCKED where settlement depends on that scope. | No derived site profile, peak, cost or dispatch-feasibility claim across the unresolved boundary. Independent, separately mapped scopes may remain assessable. |
| PV output/use is evidenced but export quantity is not measured at an identified boundary. | Report only evidenced generation/use quantities; do not manufacture an export residual unless the boundary and losses support that calculation. | Export component NOT_CALCULATED/BLOCKED. | No export, sale, feed-in credit, netting, savings or recipient claim. |
| Export quantity is metered, but interconnection/purchase terms, effective rate or payee/account applicability is missing. | The measured physical export may be shown at its identified meter and interval. | Export compensation is WITHHELD; other independent eligible cost components may be PARTIAL. | No monetary export credit or cross-account/building offset. |
| ESS SOC, charge/discharge efficiency, reserve or rating is missing/invalid for the target horizon. | A candidate that requires the unknown ESS state or hard limit is BLOCKED. Mark the overall assessment PARTIAL only when it also returns a separately identified, independently qualified scope that does not rely on that ESS action. | Do not credit ESS-dependent cost/savings; independent components retain their own status. | Never assume initial SOC, efficiency, unlimited power/capacity or terminal reserve. Show the omitted constraint and affected intervals. |
| HVAC/EV/hot-water controllability, comfort/service bounds, response or rebound is unknown. | Keep that load unchanged in the qualified candidate; it may be varied only in a clearly labeled scenario that is not reported as dispatch-feasible. Other qualified resources can still be compared. | Exclude unsupported flexibility benefits from any economic result. | No controllability, comfort/service satisfaction, feasible load shift or savings claim for the unknown resource. |
| Energy-rate evidence qualifies but the exact Pu meter window/billing-period maximum or customer applicability is missing. | Physical interval profile and horizon peak remain separately reportable. | Eligible energy components may be PARTIAL; demand component and any dependent bill-grade total remain WITHHELD/BLOCKED. | No bill-period Pu, demand charge, demand savings or complete bill total inferred from the planning interval. |
| A schedule interval crosses a tariff/time-band/effective-date boundary. | Physical interval remains on its declared UTC/site-time basis. | Split by exact overlap across applicable effective periods if source precision permits; otherwise withhold the affected economic component. | Never assign the whole interval using its start label or current/latest tariff. |
| Required source data are stale, low-quality, incomplete or clock-ambiguous. | Downgrade/block claims that depend on those observations and expose affected points/intervals. Independent evidence remains eligible only if its declared scope is separable. | Withhold dependent components; do not replace missing values with zero or a newer unpinned snapshot. | No complete/optimized assertion when a required forecast, state or measurement is unavailable. |

**Status interpretation:** `COMPLETE`, `PARTIAL`, `BLOCKED`, `NOT_CALCULATED` and `INFEASIBLE` apply to a declared assessment scope. `ALLOWED/WITHHELD` applies to each claim class. They are separate dimensions, not a universal status enum. For this proposal, `BLOCKED` means a required input/authority is unknown or unusable; `INFEASIBLE` means known hard constraints conflict with the requested candidate; `PARTIAL` means an independently valid sub-scope is returned while another declared sub-scope is blocked or excluded. Do not call an unknown ESS bound infeasible, and do not call a known violating schedule merely partial. A result must identify scope, horizon, boundary, evidence snapshot and stable reason for every withheld claim. The proposed reasons above are examples, not approved canonical codes.

**UI binding:** render qualified physical results separately from settlement/economic status; show withheld claim, reason and evidence needed next to the specific metric/action. A missing economic input must not turn a valid physical plot into a green “optimized” result, and a missing ESS constraint must not erase a separately qualified no-ESS comparison. The v0.9 prototype follows part of this pattern with explicit missing-forecast and settlement states; it does not implement a backend claim ledger.

**Evidence scope:** this matrix turns the Step 2 omissions, G1/U-001 settlement boundary, current APP-11 proposal and existing claims list into reviewable T1 semantics. It does not resolve the tariff-class/Pu unknowns, define production reason codes, authorize claims for a site, or constitute executable conformance evidence.

### Dispatch assessment / optimizer input

The optimizer boundary receives a normalized immutable assessment input containing:
- authorized internal site reference and planning window;
- physical topology and input snapshot references;
- baseline and forecast series with units, quality, source and uncertainty;
- versioned capabilities and constraints with effective time;
- optional separately resolved economic terms and objective;
- solver/policy/build identity and reproducibility settings.

It returns baseline/candidate schedules, objective-scoped diagnostics, constraint satisfaction/violations, feasibility and provenance. It does not receive credentials, tenant authorization policy, tariff legal authority or device-write access. It cannot edit/relax input constraints. A candidate is not returned as feasible when a required constraint is missing or contradictory.

### Edge data boundary

For the read-only MVP path, Edge acquires registered source data, stamps source/device/point identity and observed/received times, applies protocol/data-quality diagnostics, and forwards or buffers the evidence under an approved delivery contract. Edge owns physical command safety in the broader architecture, but APP-11 does not call that command path. The assessment service consumes canonical observations/snapshots and cannot invoke equipment writes.

The current Go Edge entrypoint only logs bootstrap startup. A protocol adapter, durable local buffer, authenticated site identity and telemetry forwarding are not established by that entrypoint.

## 5. Review and replay operations

A review command targets one immutable recommendation version and includes a disposition, optional reason/evidence references and expected version. Actor, tenant, site, permission check and review time come from trusted server context. Persist a new append-only review record; do not mutate the assessment or use the review record as command authorization.

Replay targets the original assessment and its pinned input/model/rule/schema versions. If a required reference is unavailable, return an explicit incomplete/unreplayable result. Never replace missing original dependencies with current state; preserve the original result and report divergence separately.

Possible domain notification names such as AssessmentAccepted, AssessmentCompleted or ReviewDispositionRecorded are discussion labels only. Durable state is authoritative. Transport, delivery guarantee, ordering key, retry policy and outbox/workflow mechanism are not selected by this proposal.

## 7. Proposed acceptance cases for the G7.9 Step 3 design

1. APP-11 remains separately traceable to APP-05/06/07/08; no existing operation silently changes meaning.
2. Principal/site scope is trusted and re-authorized for reads, asynchronous work, review and replay.
3. Accepted work has a durable stable reference; identical retry is idempotent; conflicting reuse is rejected.
4. Identical baseline/candidate horizon, timezone, interval boundaries, units, signs and evidence snapshot are enforced.
5. Physical schedule and financial settlement are separately represented and independently ready/blocked.
6. Missing/ambiguous mapping, stale data, missing tariffs, unknown ESS state, unverified PV rights and absent comfort limits cannot silently become favorable defaults.
7. Infeasible constraints return typed reasons and no misleading feasible candidate.
8. Review is append-only and cannot create, authorize or send a device command.
9. Replay pins the original input, mapping, model, tariff, solver, schema and policy versions; version drift or missing artifacts is explicit.
10. Tenant isolation, migration/recovery, contract compatibility and security failures are part of later executable acceptance evidence.
11. A Group B case resolves `0.2Pc + 0.8Pu` only when the customer account/class, subscribed active-demand Pc (kW), billing-period Pu evidence and applicable tariff terms are bound to the assessment. If the Pu measurement window is absent, do not borrow the planning interval; withhold the demand component and any bill-grade total that depends on it.
12. A tariff parameter such as TCA is selected by tariff scope and effective period and carries source/version provenance; a later quarter or a different class cannot silently reuse an older value.
13. PV export compensation is allowed only with site installation/tier, interconnection, export measurement, applicable purchase terms and payee/account evidence. Physical grid injection or another building's PV does not authorize a consumer-account credit or cross-site netting.

These are design acceptance requirements, not completed tests or Gate-exit evidence. The public-source facts above update the evidence inputs, not the unresolved status of U-001/U-002/U-004/U-025 or the requirement for customer Golden Bills.

## 10. Proposed logical dispatch data model

This is a schema-neutral domain proposal to close the Step 2 gaps identified above. Names below are concepts, not approved table names, JSON properties, schema IDs, or migration instructions. It extends the Step 2 foundation only where the dispatch task requires evidence, temporal lineage, and separate physical/economic results.

### 10.1 Records and ownership

| Logical record | Minimum meaning | Version / evidence rule |
|---|---|---|
| Site + physical topology revision | Authorized operating boundary; buildings, grid connection, meters, PV, ESS, end-use assets, and measured flow paths. | Effective-dated revision with evidence references. A meter can participate in the physical graph and in a separately evidenced settlement mapping; the two relationships must not be inferred from one another. PV generation, self-use, export, curtailment, storage charge/discharge and site load must use distinct quantities so one physical quantity cannot be counted twice. A logical relation to multiple sites or accounts needs explicit evidence and authorization.

### 10.2 Time, units and immutability rules

- Represent instants in a canonical UTC form and retain the site IANA timezone and clock-policy reference used to render or interpret local schedules. All assessment intervals are start-inclusive/end-exclusive; an interval end is a boundary, not an extra observed point.
- Store optimization-grid resolution separately from the applicable tariff/settlement interval. Do not average or prorate across tariff windows unless the selected tariff rule explicitly permits it.
- Every quantity declares its semantic kind, unit, sign convention, aggregation method and interval. Distinguish instantaneous power from interval-average power and energy; do not label kW as kWh or money. Any conversion requires a known duration and valid aggregation semantics.
- Preserve valid time (when a mapping, constraint or tariff applies) separately from recorded time (when the system learned it), so later evidence corrections do not rewrite a past assessment's basis.
- Assessment inputs and outputs are immutable snapshots. Corrections produce a new revision/run; human review and replay are appended records. Tenant scope is derived from trusted authorization context and enforced for synchronous reads, background work, exports and replay.

### 10.3 Step 3 design acceptance additions

Before a canonical contract or migration is created, the reviewed design should demonstrate: (1) a Site graph that reconciles with the Step 2 entity and table list; (2) an example where electrical PV flow exists but economic export credit is withheld; (3) a stale/ambiguous meter map and an unknown HVAC comfort bound producing explicit blocked/partial results; (4) two optimization intervals mapping to a different settlement interval without invented billing allocation; (5) an immutable assessment whose replay reports missing or changed dependencies without overwriting the original; and (6) cross-tenant denial across assessment, review and replay. These are proposed design/contract examples; they are not implemented tests or evidence that current services satisfy them.

The next implementation-ready artifact should be a domain-reviewed logical ER model and valid/invalid contract fixtures after the D-065 authoring/generation decision is reconciled with the G7.8 package and current contract README. 2. **Keep group-specific calculators/rules explicit.** Group A's subscribed-demand/energy structure cannot use the B/C/D demand expression. B, C and D may share a 0.2Pc + 0.8Pu form in public descriptions, but retain separate applicability, Pc/Pu updates, meter-loss adjustments, energy calendars and reactive-energy components. C's seasonal periods and D's high/low periods must be selected by tariff profile and effective period, not copied from B.
3. **Preserve evidence units and horizons.** Pc/Pu are demand quantities in kW on the billing scope; subscribed demand/eligibility may be stated in kVA; consumption is kWh and reactive energy is kvarh. Dispatch-interval peaks do not substitute for a billing-period Pu measurement without matching meter sampling and billing evidence. Group C/D reactive settlement requires supported interval/billing quantities and applicable class rules.
4. **Model EV physical load separately from EV settlement.** EV charging participates in physical interval balance using charger/feeder measurements and capability evidence. Its economic evaluation resolves the actual serving account, meter, contract and tariff, including a separately applicable transport-charging class only when evidence confirms it. Do not create a separate settlement boundary from a submeter alone, or silently place EV consumption under the building's tariff.
5. **Version TCA and other public parameters.** Effective dates and applicable tariff scope must accompany public TCA; a published rate is not a customer/account proof. Reconciliation against the actual bill/contract remains required for bill-grade economics.
6. **Keep tariff uncertainty from contaminating dispatch feasibility.** A physical schedule may be assessed for balance and device limits when tariff evidence is incomplete, but the result must mark economics unresolved and withhold bill-grade cost, savings, export credit and payback. No settlement result can be inferred from a feasible power schedule.

Proposed relationship semantics: PhysicalTopologyRevision owns physical measurement boundaries and telemetry/derived quantities. SettlementScopeRevision separately binds account/contract, installation, billing meter/channel, TariffProfileRevision, validity and applicability evidence. A physical measurement boundary can link to a settlement scope only through an evidenced association. DispatchAssessment always points to PhysicalScheduleResult and may point to a separate EconomicEvaluation. EconomicEvaluation points to a settlement scope, exact input manifest and component results. EV assets/feeder measurements join the physical schedule; EV settlement joins only when evidenced.

### Proposed invariants

1. Physical topology, measurement boundary and billed settlement scope are separate linked concepts; none is inferred from another.
2. Each economic component uses the tariff class, interval and effective dates that apply. An assessment interval is not a substitute for a CEM demand-measurement interval or billing period.
3. When a billing horizon crosses a tariff/TCA effective boundary, apply supported versioned periods or return partial/blocked economics; do not select one convenient rate for the full horizon.
4. If multiple accounts, meters or tariff profiles could apply to the same physical load and allocation rules are not evidenced, report the ambiguity and withhold bill-grade cost and savings.
5. EV charging contributes once to physical balance. Settlement follows evidence for the serving account/profile and must not duplicate the same kWh in a building account and transport-charging account.
6. PV self-consumption/export quantities describe physical flow. Export payment/credit is a separate economic component requiring interconnection, meter, purchase terms, effective rate and payee/account evidence.
7. A physical schedule may proceed with unresolved tariff evidence only when its physical inputs and hard constraints are ready; mark economics unresolved and suppress bill-grade cost, savings, payback and export value.

### Additional proposed design acceptance examples

14. Same Group C demand expression but different class/seasonal-calendar evidence selects the corresponding distinct component profile; the evaluator does not copy Group B's calendar or silently omit reactive energy.

16. EV charger has physical feeder metering but no account/contract proof: include its measured load once in physical schedule; do not attribute cost or claim a separate EV tariff.
17. EV-specific transport-charging contract is evidenced: associate load only with that scope, preserve its demand/TOU/TCA rules, and prevent duplicate settlement under the building account.
18. Dispatch horizon crosses a TCA or tariff-rule effective date: split economic intervals using the supported calendar/version or withhold the affected complete total; retain the common physical horizon.
19. PV export is physically measured but payable account is not evidenced: show physical export if supported, withhold payment/credit and cross-site allocation claims.
20. Same physical schedule is evaluated against two evidenced settlement scopes: preserve separate economic results and do not combine them into site savings without a supported aggregation rule.
