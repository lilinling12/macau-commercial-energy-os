## Executive finding

The archived G7.6–G7.8 steps often mark a **design, bootstrap plan, or code-skeleton design** complete while naming actual implementation and runtime validation as the next step. G7.7 Step 4 and Step 5 checklists explicitly left actual repository creation pending. The GitHub repository was created later and now contains a small TypeScript/NestJS, Go, and Python implementation slice plus schemas and CI.

That main-branch code is real and some of it is runtime-tested by CI, but it does not prove the archived end-to-end vertical slice was completed. In VS-001, the production-default Energy Graph adapter returns unresolved, the tariff adapter returns unresolved, evidence persistence is in-memory, and the successful path in tests uses static fixture adapters. The Go Edge command only logs startup, the Python package only defines a recommendation record/mode boundary, and the simulator directory is a README. Main explicitly says G7.2 live R0 execution is pending. There is no portal implementation, database migration tree, live PostgreSQL/NATS setup, site telemetry connector, or working grid/PV/ESS/HVAC dispatch optimizer in the inspected main tree.

### Exact scope of the VS-001 test evidence

The direct unit test source `implementation/platform-api/src/vs001/vs001.service.spec.ts` defines a synthetic telemetry event, static Energy Graph context, static MOP cost, static SHADOW optimizer with no actions and in-memory evidence. It tests the synthetic completed path, unresolved tariff fail-closed behavior, tenant mismatch rejection and deterministic evidence ID. This is useful contract/semantic evidence and supports the bounded Phase C description; it does not validate real tariff rules, data persistence, end-to-end service integration, a schedule, site physics, browser UI, measured savings or field control.

## G7.9 Step 3 consequence

G7.9 Step 2 defines baseline Tenant/Organization/Site/Building/Asset/Device/Telemetry/Optimization/Recommendation concepts and simple HTTP/event contracts. Its entity relationship sketch omits Site despite listing it; telemetry omits full quality/provenance and interval semantics; it does not define a source/load dispatch assessment contract. Step 3 is therefore not merely “split services”: it must reconcile the model and contract gaps, define module-owned API/Edge/Optimizer boundaries, and create actual repository tasks while preserving the implemented VS-001 semantics and current ADR conflict.

PR #10's APP-11 is a useful additive design input: it proposes a dispatch-assessment boundary and puts source/load comparison into the product flow. It is not the complete G7.9 Step 3 catalog, canonical wire contract, migration or runtime implementation. The Stack-neutral [local boundary design](DISPATCH-DOMAIN-AND-BOUNDARY-DESIGN-v0.1.md) expands some of this analysis; it remains a proposal outside main.

## Reconciliation and next evidence

1. **Do not label G7.6 Steps 3/5/6/7 as a completed vertical slice.** Their own `CURRENT.md` files say design/plan/blueprint complete and actual implementation/demo validation next.
2. **Treat current main as a bounded skeleton/semantic slice.** Preserve its actual Node/NestJS + Go + Python pins and test coverage, while distinguishing static test doubles from production adapters.
3. **Keep G7.9 Step 3 open.** Produce an accepted module/contract catalog, corrected tenant/site/physical/economic data relationships, versioned API schemas, persistence/migration, Edge ingestion and optimizer boundaries, and repo task/acceptance map before calling Step 3 complete.
4. **Do not call the G7.6 demo/MVP ready until the whole agreed first slice passes on the exact commit:** real local simulator, Edge forwarding, durable DB storage, resolved fixture-driven tariff path, deterministic bounded optimizer, recommendation UI, audit/replay and tenant negative checks, all in an integrated runtime.
5. **For the requested commercial product, the first demonstrable user journey must add schedule comparison** for evidenced grid/PV/ESS/HVAC resources, while keeping tariff settlement and claims evidence-bounded and actions SHADOW-only. The early G7.6 HVAC recommendation slice can be a data/telemetry foundation, not the acceptance criterion for the intended product experience.
